How gradients actually reach early layers in a ResNet

Lesson 7 companion diagram — object-recognition course

The objection that started this page "It sounds like early layers are not really 'closer' in number of steps to the gradient computed from the cost function" — raised while reading the Lesson 7 concept notes on freezing layers and skip connections. It's a fair objection: counting arrows, skip connections really don't shorten the path from input to loss. This page exists to show what does change instead.

Your objection is correct as stated: a skip connection does not make the first convolutional block fewer hops away from the loss. Count the arrows from input to loss in the diagram below — it's 4, with or without skip connections. What changes isn't the hop count. It's that each hop now has two possible routes, and one of the many combinations you can pick never multiplies the gradient by anything smaller than 1.

Symbols used on this page

x — the input to whichever block is currently being discussed (not necessarily the whole network's input image — just "what this block receives").

y — that same block's output: y = x + F(x) (then usually passed through a final ReLU).

F — the residual branch: the specific stack of weight layers inside one block (Conv→BN→ReLU→Conv→BN, see section 3) that gets added to x. Every block has its own F, with its own learned weights — it's a placeholder name for "this block's conv layers," not one fixed function shared by the whole network.

L — the loss: the single scalar at the very end of the entire network (after every block, pooling, and the classification head) that training minimizes. Computed once per forward pass, not once per block — the same L from Lesson 4's CrossEntropyLoss. Strictly, "L" is a number, but writing ∂L/∂x only makes sense by treating it as the output of a function of x (everything downstream, composed together) — same loose convention as writing dKE/dv for kinetic energy KE = ½mv²: one symbol doing double duty as "the formula" and "the value you get out of it."

I — the identity matrix: the "do nothing" operator. Multiplying anything by I returns that same thing, unchanged.

J (also written ∂F/∂x) — the Jacobian of F: the matrix of F's own partial derivatives, i.e. how much each output of F moves when each input to F is wiggled.

r, N, k — only used in the toggle demo in sections 1-2: r=0.6 is a made-up stand-in for "how much a typical weight path shrinks gradient," N=4 is the toy network's block count, and k is how many blocks you've set to "weight path" in the toggle.

1. The network, with both routes drawn

weight path (F): multiplies gradient by its Jacobian, assume ≈ r = 0.6 per block identity / skip path: multiplies gradient by exactly 1

2. Pick a route at each block — the hop count never changes

Click a block to flip which route is highlighted for it. There are 24 = 16 such combinations in total (this is the "ensemble of paths" view of a ResNet) — this toggle just lets you walk through a few of them.

The actual point No matter which buttons you press, the path from x to L is always 4 hops — skip connections don't shorten that. What they add is a second edge at every hop whose derivative is exactly 1 instead of <1. The real gradient reaching x is the sum over all 16 combinations, not just the one you've selected — and crucially, the all-skip combination (press every button to "skip") contributes a term of exactly 1, independent of depth. Make the network 50 blocks deep instead of 4, and that term is still exactly 1 — it's the one path in the sum that never vanishes, which is what keeps the whole sum from vanishing even as the mostly-weight-path terms shrink toward zero.

3. Zooming into one block

y = ReLU(x + F(x)). Differentiating: ∂y/∂x = ∂F/∂x + I (ignoring the outer ReLU for a block where it's active). That + I is the dashed line — a literal identity matrix added into the Jacobian at every single block, regardless of how deep the network is.

In plain terms, for a single number instead of a tensor: if y = x + F(x), basic calculus says dy/dx = dF(x)/dx + dx/dx = F'(x) + 1 — derivative of a sum is the sum of derivatives, nothing more exotic than that. I is just the tensor/matrix version of that "+1": wiggling x directly changes y by the same wiggle, dimension for dimension, since x is literally added into y unchanged.

4. Why this doesn't happen in a plain (non-residual) CNN

In a plain stack of conv blocks, each block's Jacobian is ∂F/∂x only — there is no + I term. The gradient reaching the input is a product of N of these Jacobians with no alternative route, so if each one has norm r < 1, the product shrinks as rN and nothing stops it from vanishing as N grows. The skip connection doesn't reduce N — it just guarantees that one term in the expanded sum of paths is never part of that shrinking product.

5. Does training "skip" the block — forward, backward, or both?

No. Neither pass ever skips the block's computation. This is worth stating plainly because the toggle in section 2, and the "16 combinations" framing, can make it sound like training literally picks one route per block. It doesn't.

Forward pass: for every single example, every single block computes F(x) in full (both convs, both BatchNorms, the inner ReLU) and passes x through unchanged, then adds them: y = F(x) + x. The block's weight layers always run — "skip connection" describes the wiring (x has a route around the block), not a runtime choice to bypass it.

Backward pass: gradient flows through both branches, every time, and the two contributions are added: ∂L/∂x = ∂L/∂y · (∂F/∂x + I) — (gradient through the conv layers) plus (gradient passed straight through, unchanged). Nothing is dropped here either.

"Downstream" and "upstream" just mean "which way along the arrow in section 1." The forward pass runs input → block 1 → block 2 → … → loss, left to right. Downstream of this block means anything further to the right — closer to the loss, computed after this block runs. Upstream means anything further to the left — closer to the input, computed before this block.

Backprop runs right to left: it starts at the loss and hands each block a number that says "here's how much the loss changes per unit change in your output" — that is ∂L/∂y, and it comes from downstream (the block to this one's right, and ultimately the loss itself), since those are the only things standing between this block's output y and the loss L. This block's job is to convert that into "here's how much the loss changes per unit change in my input" — ∂L/∂x — and hand that further upstream, to the block on its left. (∂F/∂x + I), from the "plain terms" note in section 3, is the conversion factor. Read the whole line as: "what I pass upstream equals what I received from downstream, times my own local derivative."

Formal proof of ∂L/∂x = ∂L/∂y · (∂F/∂x + I)

Setup: x, y ∈ ℝn, y = x + F(x) for differentiable F: ℝn → ℝn, and L is a scalar depending on x only through y (everything downstream of this block is already folded into "how L depends on y").

Step 1 — differentiate y coordinate-wise. For each j: yj = xj + Fj(x), so by the sum rule:

dyj  =  dxj + Σi (∂Fj/∂xi) dxi

Step 2 — chain rule for L. L depends on x only via y, so:

dL  =  Σj (∂L/∂yj) dyj

Step 3 — substitute Step 1 into Step 2 and group every term by which dxi it multiplies:

dL  =  Σj (∂L/∂yj) [ dxj + Σi (∂Fj/∂xi) dxi ]
  =  Σi [ (∂L/∂yi) + Σj (∂L/∂yj)(∂Fj/∂xi) ] dxi

Step 4 — match coefficients. By definition dL = Σi (∂L/∂xi) dxi. The xi are independent variables, so the two expressions for dL can only agree for every possible dx if the coefficients match term by term:

∂L/∂xi  =  (∂L/∂yi) + Σj (∂L/∂yj)(∂Fj/∂xi)

Step 5 — recognize this as a matrix product. Write ∂L/∂y as a row vector and J for the Jacobian of F (entries Jji = ∂Fj/∂xi). The sum Σj (∂L/∂yj) Jji is exactly the i-th entry of (∂L/∂y)·J, and (∂L/∂yi) is the i-th entry of (∂L/∂y)·I. Entry by entry, that's:

∂L/∂x  =  (∂L/∂y)·I + (∂L/∂y)·J  =  ∂L/∂y · (∂F/∂x + I)

∎ — exactly the line quoted above. Nothing here used any special property of F beyond differentiability — the +I comes purely from y containing an unmodified copy of x added into it. (For a real conv block, x and F(x) are tensors, not flat vectors — flatten every spatial/channel index into one long vector and the exact same algebra goes through unchanged, just with more indices to sum over.)

So where does the "16 paths" idea in section 2 come from, if nothing is ever skipped? It's an algebraic fact, not a computational one. Stack N blocks and the full Jacobian from output to input is a product of N matrices, each of the form (I + Ji). Multiply that product out by hand and it expands into a sum of 2N terms — one term per subset of blocks whose Ji you keep, the rest replaced by I in the expansion. PyTorch never computes this expansion, and never runs 2N passes — autograd just multiplies the real Jacobians once, in the order the blocks actually ran, exactly as described above. The expansion is a way for us to understand why that one multiplication doesn't vanish; the toggle lets you inspect individual terms of it for intuition — it isn't simulating 16 different training runs.

A technique that does literally skip a block's computation at random during training is stochastic depth (Huang et al., 2016) — for some training batches a block is replaced with a true identity (no F(x) computed, so there's nothing to backprop through), with probability increasing for deeper blocks, and every block is used at test time. It's a real, deliberate design choice built on top of ordinary ResNets — not what happens by default, and not something this course covers, but worth knowing the name of so it doesn't get conflated with vanilla skip connections.
